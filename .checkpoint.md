# CHECKPOINT — Contexto para o assistente

## Projeto
**XeMonitor** — Aplicação Zig que lê scanner Honeywell 1900 (Granit) via CH340 (USB-Serial) e injeta como teclado no Windows.

## Hardware
- Scanner: Honeywell 1900 (Granit) via adaptador CH340 USB-Serial
- Porta Windows: COM4 (o driver CH340 no Windows está quebrado — erro 31 / AccessDenied)
- Fluxo ativo: **WSL2 bridge** — WSL2 (Arch) lê `/dev/ttyUSB0` e serve TCP na porta 9000; o Windows conecta com `--tcp` e injeta via `SendInput` (Win32 nativo)

## Problema original (histórico, NÃO RESOLVIDO no Windows)
Driver CH340 no Windows corrompido: `SetCommState` erro 31, libserialport AccessDenied, PuTTY erro 5. Contornado pelo TCP bridge WSL2. Se um dia quiser voltar ao acesso direto, é preciso reinstalar/diagnosticar o driver CH340.

## Sessão no CachyOS (Linux host de dev/teste) — CONCLUÍDO
- **Fix TCP** em `src/main.zig` (arm `.tcp`): `rbuf [0]u8` — o `netRead` do Zig anexa o buffer interno do reader como 2º iovec; com reader novo por byte, o byte extra era descartado → `'TSSA00'`. Com rbuf vazio, lê só o destino. Provado com fake server e scan real.
- **End-to-end no Linux (systemd)**: unit de usuário `~/.config/systemd/user/xemonitor-bridge.service` com `ExecStart=/usr/bin/sg uucp -c '<repo>/zig-out/bin/bridge'` (wrapper dispensa re-login — sessão antiga não herdou grupo `uucp`). `systemctl --user enable --now` → active, `/dev/ttyUSB0` aberto, porta 9000.
- **Scan físico validado 2x** (`7898121840147`): `[scan] '<código>'` completo → `[info] injected` → `[info] enter sent` → texto no **Kate** (foco obrigatório: ydotool digita onde está o foco; o log `injected` não garante foco no editor).
- **Bridge é musl estático** (Zig linka musl por padrão): `readelf` sem dynamic interpreter → roda em glibc e musl (Alpine) sem recompilar.
- Observação: `runCommand` no main.zig não checa exit code do ydotool — `injected` não é prova de entrega ao alvo (ok, pois o alvo depende de foco).
