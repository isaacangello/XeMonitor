## Projeto
**XeMonitor** — Aplicação Zig que lê scanner Honeywell 1900 via CH340 (USB-Serial) e injeta como teclado no Windows.

- Conexão: CH340 USB-Serial (USB do scanner ligado num adaptador CH340)

### 3. Correção WinAPI serial (`src/main.zig:524-620`)

  - `Sleep(100)` antes de configurar

  - Loga `@sizeOf(w.DCB)` pra debug

## Problema atual (NÃO RESOLVIDO)
**SetCommState retorna erro 31 (ERROR_GEN_FAILURE) no CH340 via WinAPI.**
**Driver CH340 também falha no .NET SerialPort.Open() — "dispositivo não está funcionando".**

### Diagnóstico do driver (27/05/2026)
- **Driver detectado**: CH341S64.SYS v3.9.2024.9 (04/11/2024), serviço `CH341SER_A64`
- **Device Manager**: Status OK, problem CM_PROB_NONE
- **mode COM4**: lê config (115200 8N1, DTR=OFF, RTS=ON)
- **.NET SerialPort.Open()**: FALHA em 115200 e 9600 — "Um dispositivo conectado ao sistema não está funcionando"
- **Disable/Enable cycle**: não resolveu
- **Terminal**: Admin = True
- **Processos suspeitos**: nenhum segurando COM4
- **Manual baixado**: 2706121.pdf (Honeywell 1900)

### Testes realizados (27/05/2026)
- **Reinstalação do driver CH340**: mesma versão 3.9.2024.9 — **não resolveu**
- **xemonitor.exe --winapi**: erro 31 (ERROR_GEN_FAILURE) em SetCommState, mesmo com fallback DTR/RTS=0
- **xemonitor.exe (libserialport)**: AccessDenied na COM4
- **PuTTY serial COM4 115200**: erro 5 (acesso negado)
- **conclusão**: driver Windows CH340 corrompido/incompatível, mesmo assinado pela Microsoft

### Solução implementada: TCP bridge WSL2 → Windows

#### Como funciona
1. **WSL2** lê `/dev/ttyUSB0` (CH340) via Python + `termios` (stdlib) e serve via TCP na porta 9000
2. **Windows** (xemonitor.exe) conecta via `--tcp 127.0.0.1:9000` e injeta teclas normalmente

#### Arquivos novos/modificados
- `src/main.zig` — adicionado `--tcp <HOST:PORT>`, nova variante `SerialConnection.tcp`, função `connectTcp()`
- `src/bridge.py` — bridge Python (stdlib, sem dependências extras) que lê serial e serve TCP
- `run_bridge.bat` — script completo: inicia bridge WSL2 + xemonitor + Bloco de Notas
- `stop_bridge.bat` — mata todos os processos do bridge

## Comandos úteis

```cmd
:: Compilar
zig build

:: Rodar com TCP bridge (WSL2)
run_bridge.bat

:: Rodar direto via TCP
zig-out\bin\xemonitor.exe --tcp 127.0.0.1:9000

:: Bridge manual no WSL2
wsl python3 src/bridge.py

:: Rodar com libserialport (COM local, padrão)
zig-out\bin\xemonitor.exe

:: Rodar com WinAPI
zig-out\bin\xemonitor.exe --winapi

:: Rodar com porta específica
zig-out\bin\xemonitor.exe --port COM4

:: Ver log
type xemonitor.log

:: Parar tudo
stop_bridge.bat
```

## Sessão 27/05/2026 — Testes com TCP bridge

### O que foi feito
1. `zig build test` — testes passaram sem erros
2. `zig build run` — xemonitor tentou reconexão TCP (bridge não estava rodando)
3. Bridge Python no WSL2 testada manualmente: abre `/dev/ttyUSB0`, configura serial 115200 8N1, serve TCP na porta 9000
4. Bridge ACEITOU conexão de xemonitor via `127.0.0.1:9000` (localhost forwarding funciona)

### Problema encontrado
- **Bridge só aceita UMA conexão** — `sock.accept()` é chamado uma vez só; após aceitar, novas conexões são recusadas
- **Sequência correta**: matar bridge + xemonitor → iniciar bridge → conectar xemonitor
- `run_bridge.bat` precisa vincular no IP do WSL2 (não 127.0.0.1) — IP atual: `172.19.146.218`
